## Mini App — ПОЛНОФУНКЦИОНАЛЬНЫЙ магазин (v25)

TMA теперь умеет ВСЁ то же, что и бот, — весь путь покупки происходит
внутри Mini App, чат остаётся параллельным (запасным) каналом:

1. Каталог → сервис → тариф (как было);
2. Оформление прямо в TMA: карточка заказа со скидкой новичка и бонусом
   за друзей, ввод и применение промокода, список способов оплаты
   (Gram / USDT / карта / Stars — ровно те, что включены в боте);
3. Оплата внутри TMA:
   • **Gram/USDT** — сумма, адрес, комментарий и кнопки «Открыть
     Tonkeeper / Gram Wallet», копирование в один тап, таймер 30 минут;
   • **Карта через Tribute** — кнопка оплаты открывает Mini App Tribute
     прямо в Telegram; **через Digiseller** — ввод email → ссылка оплаты;
   • **Telegram Stars** — нативный счёт через `WebApp.openInvoice`
     (создаётся `create_invoice_link`, XTR, без провайдера);
4. Живой статус заказа: шаги «Оплата → Данные → Активация → Готово»,
   автополлинг каждые 5 секунд — экран сам перескакивает на следующий
   шаг, когда поллер бота подтвердил оплату или админ активировал заказ;
5. Ввод данных аккаунта в TMA (форма из `account_fields` каталога) —
   данные шифруются и попадают в заказ так же, как ввод в чате;
   админы получают то же уведомление;
6. «Мои заказы» — история с чипами статусов; «Профиль» — бонусный счёт,
   скидка новичка, реферальная ссылка с копированием и кнопкой
   «Поделиться» (`t.me/share`), статистика приглашений, поддержка.

### Что НЕ дублируется
Единственный источник истины — код бота. TMA вызывает те же функции:
`db.create_order`, `get_welcome_discount`/`calc_bonus_use`,
`validate_promo_code`/`calculate_discounted_price`, `generate_memo`/
`generate_tonkeeper_link`, `verify_payment`, `tribute.create_order`/
`is_order_paid`, `digiseller.create_payment_url`/`find_payment_for_order`,
`try_transition_order_status` (CAS), `_post_payment_actions` (лоялти,
реферальный бонус, промокод), `extinguish` (гашение платёжных экранов
в чате). Поллеры бота по-прежнему подтверждают оплаты сами — кнопка
«Проверить оплату» в TMA лишь ускоряет реакцию.

### API (все — POST, кроме каталога; все требуют валидный initData)
```
GET  /api/catalog               публичный каталог
POST /api/session               initData → профиль + конфиг способов оплаты
POST /api/order                 создать заказ (скидки как в select_plan)
POST /api/orders                история заказов (до 50)
POST /api/order/{id}/info       карточка заказа (+реквизиты, +поля формы)
POST /api/order/{id}/promo      применить промокод
POST /api/order/{id}/pay        начать оплату: ton|usdt|card|stars (+email для Digiseller)
POST /api/order/{id}/check      ручная проверка оплаты (антифлуд 10 с, как в боте)
POST /api/order/{id}/account    сохранить данные аккаунта → pending_activation
POST /api/order/{id}/cancel     отменить неоплаченный заказ
POST /api/profile               бонус, рефералка, скидка новичка
```

### Безопасность
- как в v23: HMAC-SHA256 initData (окно 60 минут), rate-limit 5 заказов/
  10 минут, антифлуд проверок 10 с (тот же `check_cooldown_left`);
- НОВОЕ: каждый `/api/order/{id}/*` проверяет владение
  (`order.user_id == telegram_id` из подписи) — чужой заказ не виден;
- данные аккаунта принимаются ТОЛЬКО для оплаченных заказов
  (`pending_account`) и шифруются тем же Fernet-ключом.

- `webapp/index.html|style.css|app.js` — 6 экранов (каталог, сервис,

## Mini App — веб-магазин (v23)

Бот получил полноценный веб-магазин в стиле ton.org / gramcoin.org:
тёмно-синий фон со свечениями, TON-синие градиентные кнопки, крупные
карточки сервисов с брендовыми цветами. Открывается прямо в Telegram
кнопкой «🛍 Магазин» (круглая кнопка меню + первая кнопка reply-клавиатуры).

### Архитектура «тонкого клиента»
Mini App показывает каталог и создаёт заказы. ВСЯ платёжная логика
(TON/USDT/карта/Tribute/Stars, поллеры, активация) остаётся в боте:

1. Покупатель выбирает сервис и тариф в Mini App;
2. `POST /api/order` применяет те же скидки, что и в чате
   (скидка новичка 10% + бонус за друзей с резервом), и создаёт заказ
   той же `db.create_order()` — тот же пайплайн, та же таблица;
3. Бот сам отправляет покупателю в чат стандартный экран выбора
   способа оплаты (`payment_method_kb` / `promo_code_kb`);
4. Дальше заказ живёт как обычный: поллеры, проверка оплаты,
   запрос данных аккаунта, активация, напоминания.

Плюс: заказ из веба и заказ из чата неотличимы для остального кода.
Минус отсутствует: Mini App не дублирует ни строчки платёжной логики.

### Файлы
- `webapp/index.html`, `webapp/style.css`, `webapp/app.js` — фронтенд
  Mini App (zero-build: чистые HTML/CSS/JS, без Node на сервере).
  Вне Telegram работает в демо-режиме (превью дизайна, покупки отключены);
- `webapp_api.py` — API: `GET /api/catalog` (публичный),
  `POST /api/session` (валидация initData + профиль),
  `POST /api/order` (создание заказа + счёт в чат). Монтируется в
  health-сервер (`main.start_health_server`), тот же порт, CORS не нужен;
- статика магазина: `{WEBAPP_URL}/app/`.

### Безопасность
- initData проверяется HMAC-SHA256 по алгоритму Telegram
  (`secret = HMAC("WebAppData", bot_token)`), окно свежести 60 минут —
  украденный initData бесполезен через час;
- rate-limit: не более 5 заказов за 10 минут с одного пользователя;
- каталог публичный, все пользовательские операции — только с валидной
  подписью; без BOT_TOKEN API заказов не работает.

### Настройка (в .env)
```
WEBAPP_URL=https://ваш-домен          # базовый URL health-сервера, БЕЗ /app/
STORE_NAME=SUBSTORE                   # название магазина в шапке (опция)
```
Если `WEBAPP_URL` задан — при старте бот ставит кнопку «🛍 Магазин» в меню
чата и в reply-клавиатуру. Если пусто — бот работает как раньше, магазин
доступен только по прямой ссылке `{WEBAPP_URL}/app/`. Требования прежние:
открытый HTTP-порт (Render Free уже подходит) + HTTPS (Telegram открывает
Mini App только по https).

### Тесты
`scripts/test_webapp_api.py` — 12 проверок: статика, каталог, отказ без
подписи/с подделанной подписью, создание заказа (со скидкой новичка),
отправка счёта в чат, rate-limit, 404 тарифа. Полная регрессия 25/25.

## Проблема 3 (РЕЛИЗ-АУДИТ): заказ оплачен, но запрос данных аккаунта не дошёл

### Причины (найдено полным аудитом флоу продажи)
1. **Хрупкая отправка запроса данных.** Фоновые авто-проверщики оплат в
   main.py после подтверждения оплаты отправляли юзеру сообщение «Введите
   данные аккаунта» БЕЗ защиты. Любая сетевая осечка или ошибка HTML →
   заказ уже переведён в pending_account, но юзер НИЧЕГО не получил, и
   на следующем цикле заказ больше не проверялся. Результат: деньги
   получены, юзер брошен без единого сообщения.
2. **Гонка с очистителем просроченных заказов.** Gram/USDT-заказы
   отменяются через 30 минут. Если юзер заплатил на 29-й минуте, а
   блокчейн подтвердил платёж на 31-й — заказ уже отменён, переход
   невозможен, оплата «пропадала».
3. **Недоплаты молча терялись.** Если карточный платёж приходил на
   меньшую сумму, авто-проверка просто пропускала заказ: ни юзер, ни
   админ не узнавали, заказ висел вечно.
4. **Сломанные имена сервисов роняли сообщения.** Если в каталоге у
   сервиса/тарифа в названии есть символы `<`, `>`, `&` — все сообщения
   с этим заказом не проходили HTML-разбор, юзер получал тишину.

### Решения
1. **`_send_account_input_prompt()` в main.py** — защищённая отправка
   запроса данных: 3 попытки + автоматический переход на ОБЫЧНЫЙ ТЕКСТ
   (без HTML), если Telegram отвергает разметку + все имена экранированы
   через safe_html.
2. **Новый фоновый «спасатель» `pending_account_notifier`** — каждую
   минуту ищет оплаченные заказы (pending_account), которым запрос данных
   так и не доставлен (флаг account_prompt_sent в БД), и ДОСТАВЛЯЕТ его.
   Теперь запрос данных получает 100% оплаченных заказов, даже если
   авто-проверка упала сразу после подтверждения оплаты. Бонус: всем
   «застрявшим» старым заказам запрос придёт после первого запуска.
3. **Восстановление отменённых оплаченных заказов** — если платёж
   подтверждён, а заказ уже отменён по таймауту, авто-проверка
   переводит его обратно в pending_account и уведомляет админа.
   Дополнительно очиститель теперь не трогает заказы, истёкшие менее
   10 минут назад (грейс-период).
4. **Недоплаты (underpaid) не теряются** — юзер и админ получают
   уведомление (один раз), в заказ пишется комментарий для панели.
   То же самое в ручной проверке «Проверить оплату».
5. **Экранирование имён** во всех 17 местах сообщений заказов.

## Проблема 2: ошибка «query is too old and response timeout expired»

### Причина
Когда связь бота с Telegram нестабильна (падает прокси/сеть — в логе это
`ServerDisconnectedError`), клики юзера по inline-кнопкам доходят до бота
с опозданием больше 10 секунд. Telegram разрешает отвечать на клик
(callback query) только в первые секунды, поэтому ответ бота отвергается:

    TelegramBadRequest: Bad Request: query is too old and response
    timeout expired or query ID is invalid

и обработка апдейта падает целиком (юзер не видит уведомления).

### Решение
1. **Новый модуль `utils/safe_callback.py`** — функция `safe_answer()`:
   работает как обычный `callback.answer()`, но ошибку «протухшего»
   запроса молча проглатывает, а осмысленный текст (например,
   «Оплата уже подтверждена!») отправляет обычным сообщением, чтобы
   юзер всё равно получил отклик.
2. **Все 98 вызовов `callback.answer()`** в `user_handlers.py` и
   `admin_handlers.py` переведены на `safe_answer()`.
3. **Глобальный обработчик ошибок в `main.py`** (`@dp.error()`):
   дополнительно страхует — «query is too old», «message is not modified»
   и «bot was blocked» не роняют обработку апдейтов и не мусорят логами.

## Главная проблема 1 — бот не принимал почту/данные аккаунта после оплаты

### Причина
Оплата подтверждается автоматически фоновыми задачами `crypto_payment_poller`
и `digiseller_payment_poller` (файл `main.py`). Эти задачи работают ВНЕ системы
диалогов aiogram (FSM), поэтому после авто-подтверждения оплаты они присылали
сообщение «Введите данные аккаунта», но состояние ввода (`waiting_for_account_fields`)
не устанавливали.

Обработчик ввода данных срабатывает ТОЛЬКО при установленном состоянии.
Итог: юзер пишет почту → сообщение не совпадает ни с одним обработчиком →
бот молча игнорирует. Ручная кнопка «Проверить оплату» работала, потому что
устанавливала состояние, — а авто-проверка (основной путь) — нет.

### Решение
В конец `handlers/user_handlers.py` добавлен страховочный обработчик
`account_input_fallback`: он ловит любые текстовые сообщения, которые не
поймал ни один другой обработчик, и если у юзера есть оплаченный заказ со
статусом `pending_account` — воспринимает текст как ввод данных аккаунта и
запускает обычный сценарий (включая все следующие поля: пароль и т.д.).

Это также чинит ввод данных после `/start` и после перезапуска бота
(память состояний MemoryStorage очищается при каждом рестарте).

## Исправление: бот просил логин/пароль ДО оплаты (Digiseller, v6)

ложно «подтверждал» новый заказ по СТАРОМУ платежу и переводил его в

  проставляет момент создания ссылки на оплату (UTC).
- `services/digiseller.py` — `find_payment_for_order` принял параметр

- `handlers/user_handlers.py` + `main.py` — оба места проверки

## Новое: оплата картой через Tribute Shop API (v7)

### Что это
Альтернатива Digiseller для приёма карточных платежей (комиссия Tribute
10% вместо ~24% у Digiseller). Включается ключом: если в `.env` задан
`TRIBUTE_API_KEY` — кнопка «Банковская карта» работает через Tribute;
если ключа нет — по-прежнему через Digiseller. Ничего в коде отключать
не нужно.

### Почему это надёжнее
Каждый заказ имеет собственный UUID в Tribute. Подтверждение оплаты —
точный запрос статуса ИМЕННО этого заказа (GET /shop/orders/{uuid}),
никаких подбо́ров по email/сумме. Класс багов «бот запросил логин/пароль
до оплаты» здесь невозможен по построению (покрыто тестом T4 в
scripts/test_tribute.py).

### Как подключить
1. Открой @tribute → веб-приложение → Настройки (⋯) → «Управление
   API-ключами» → «Сгенерировать API-ключ».
2. Добавь в `.env`:
   ```
   TRIBUTE_API_KEY=твой_ключ
   # TRIBUTE_SHOP_ID=123          # опционально: если магазинов несколько
   # TRIBUTE_CHECK_INTERVAL=15    # опционально: период опроса, сек
   ```
3. Перезапусти бота. В логе появится «Tribute config: ...».

Публичный домен НЕ нужен: бот сам опрашивает статусы (подходит для
локального запуска). Вебхуки можно добавить позже при переезде на VPS.

### Как выглядит для покупателя

картой» (открывает Mini App Tribute прямо в Telegram; карты/СБП/Wallet)
→ после оплаты бот сам подтверждает заказ за ~15–30 сек и просит данные
аккаунта. Email не нужен вовсе. Кнопка «Проверить оплату» — для
нетерпеливых.

### Гарантии целостности
- CAS-переход pending_payment → pending_account: двойное подтверждение
  исключено (тест T6).
- Заказ, отменённый по таймауту, но оплаченный (например, бот был

- Лимиты Tribute: 100 – 300 000 ₽ на заказ (вне лимитов — понятная

## v11 — Drip-движок: без залпов и повторов + уточнения Tribute по докам

### Проблема

3. Попутно найдены 2 бага drip-движка: из-за сравнения дат в разных

   isoformat с «T»; пробел < «T») drip_1h уходил СРАЗУ после /start,
   а проверка last_drip_sent не мешала ПОВТОРНОЙ отправке drip_1h

### Что сделано (`services/marketing.py`, `config.py`)

Drip-движок переписан, 4 уровня защиты от спама:
1. **Строгая лестница касаний** (`_NEXT_DRIP` по last_template):

   каждая стадия (1ч → 24ч → 72ч) уходит РОВНО ОДИН раз, по порядку.
2. **Возрастной фильтр** `DRIP_MAX_USER_AGE_HOURS=96`: юзеры старше
   никогда не получают drip — старая база молчит.
3. **Минимальная пауза** `DRIP_MIN_GAP_HOURS=24` между касаниями:
   юзерам, «догнавшим» после офлайна, стадии приходят с интервалом.
4. **Единый формат дат** с SQLite (`%Y-%m-%d %H:%M:%S`) в cutoff и
   mark_drip_sent — сравнения теперь хронологически корректны.

Итоговое расписание для нового юзера: drip_1h — через час после
/start, drip_24h — через сутки, drip_72h — через трое; после покупки
или трёх касаний — тишина навсегда.

## v10 — Политика чата: стираются ТОЛЬКО дубли, в админке не стирается ничего

### Проблема
Владелец: «это слишком уж. Стираться должны сообщения которые дублируют одно
и то же. Например постоянное открытие каталога. А в админке то что удаляется
это вообще не позволительно». До v10 бот «растворял» десятки сообщений по
таймеру (подтверждения, ошибки, подсказки, карточки заказов у админа —
70+ точек), и админский лог регулярно самоуничтожался.

### Решение: дедупликация вместо таймерного удаления
Единственная форма стирания теперь — дубликаты. Если бот отправляет в один
и тот же личный чат сообщение с тем же содержимым, что и раньше (юзер в
N-й раз открыл каталог / повторил команду / заново открыл оплату того же
заказа), предыдущая копия стирается — в истории остаётся одна свежая.

#### 1. Session-middleware `DuplicateCleanupMiddleware` (`utils/chat_dedup.py`, новый)
- Перехватывает исходящие `send_message` (по тексту+parse_mode) и
  `send_photo` (по подписи) на уровне `bot.session` — работает для ЛЮБОЙ
  отправки: `message.answer`, рассылки, drip, ответы поддержки.
- Реестр в памяти: (chat_id, сигнатура) → последний message_id (TTL 24 ч,
  максимум 4096 записей). Повторная отправка того же контента стирает
  прошлую копию ДО отправки новой.
- НЕ затрагиваются: админские чаты (chat_id ∈ ADMIN_IDS — никогда ничего
  не удаляется), группы/каналы, фото без подписи.
- Регистрация: `bot.session.middleware.register(...)` в `main.py`.

#### 2. Команды юзера: `UserCommandDedupMiddleware` (замена v9-растворения)
- Повторная отправка ТОЙ ЖЕ команды стирает её предыдущую копию
  («/catalog» и «/catalog@Bot» — одно и то же; повторный «/start ref_xxx»
  тоже дубликат команды /start). Разовые команды остаются в чате навсегда.
- Обычный текст юзера (email, промокод, логин/пароль) не трогается.
- Админским чатам не применяется.

#### 3. Удалены ВСЕ таймерные автоудаления
- `admin_handlers.py` — 44 точки (карточки заказов 120с, статистика 60с,
  меню 3с, «Готово», ошибки, /adhelp и т.д.) — админский лог неприкосновенен.
- `user_handlers.py` — 15 точек (ошибки, подсказки, подтверждения).
- `support_handlers.py` — 3 точки («Готово» тикетов).
- `main.py` — уведомление об истёкшем заказе больше не стирается.
- QR-cleanup отменён: бот не удаляет QR-фото после оплаты/отмены.
  Повторное открытие оплаты того же заказа стирает старый QR благодаря
  НОВЫМ подписям с номером заказа («QR-код оплаты заказа #N»), а QR разных
  заказов различаются и не мешают друг другу.
- `utils/auto_delete.py` удалён целиком (механизм растворения не нужен).

### Конфиг
- `.env` → `CHAT_DEDUP_ENABLED=false` — полностью выключить стирание дублей
  (тогда бот не удаляет вообще ничего, нигде). Дефолт: true.
- Старый флаг `USER_COMMANDS_AUTODELETE` упразднён.

### Изменённые файлы
- `utils/chat_dedup.py` — НОВЫЙ: реестр, сигнатуры, оба middleware
- `utils/auto_delete.py` — удалён
- `main.py` — регистрация обоих middleware, без автоудалений
- `config.py` — `CHAT_DEDUP_ENABLED` вместо `USER_COMMANDS_AUTODELETE`
- `handlers/admin_handlers.py` / `user_handlers.py` / `support_handlers.py` —
  без единого автоудаления; QR-подписи с номером заказа
- `.env.example` — новый флаг

### Тесты
`scripts/test_chat_dedup.py` — 37 проверок: сигнатуры (текст/фото/команды,
админ и группа не трогаются), реестр и TTL, сценарий «трижды открыл каталог
→ осталась одна копия», уникальные сообщения не удаляются, админский чат
не трогается, команды стираются только как дубли, обычный текст/группы не
трогаются, флаг off выключает всё, регистрация в main.py, отсутствие
автоудалений в коде. Регрессия: chat_cleanup(5), cosmetics(36), functional,
release, smoke, support_feature — PASS.

## v12 — UX платёжного флоу: гашение мёртвых экранов, дедуп кнопок меню, кулдаун проверки, устаревшие кнопки

### Проблемы
1. После оплаты платёжные экраны оставались «живыми» с мёртвыми кнопками:
   QR-фото висело с надписью «наведите камеру», а кнопки «Проверить оплату»
   / «Оплатить» вели в попапы «Оплата уже подтверждена!» / «Заказ отменён».
   Особенно заметно при авто-подтверждении фоновым поллером — он присылал
   новое сообщение, а старый экран оставался нетронутым.
2. Повторные нажатия кнопок меню оставляли столбик «Каталог», «Каталог»,
   «Каталог» — дедуп v10 чистил только ЭКРАНЫ бота и команды «/…», но не
   собственные тексты-нажатия юзера.
3. Юзеры спамили «Проверить оплату» каждые 1–2 секунды — каждая проверка
   бьёт во внешний API (блокчейн/Tribute/Digiseller).
4. Нажатие устаревшей инлайн-кнопки (после смены версии/рестарта) молча
   висело с «часиками» — юзер думал, что бот завис.

### Решения

#### 1. Гашение платёжных экранов — `utils/payment_ux.py` (НОВЫЙ)
- Бот запоминает message_id каждого платёжного экрана заказа (текст с
  кнопками TON/USDT/Digiseller/Tribute и QR-фото) в реестре (TTL 24 ч,
  кап 2048 записей; переоткрытие экрана не плодит записей).
- После успешной оплаты экраны «гасятся» РЕДАКТИРОВАНИЕМ (ничего не
  удаляется — политика чата не нарушается, история покупок остаётся):
  текстовый экран → короткое «✅ Оплата заказа #N подтверждена» без
  кнопок; QR-фото → подпись «✅ QR-код заказа #N — оплата подтверждена»
  (фото-квитанция остаётся).
- Основной экран, который обработчик проверки САМ переоформил в
  rich-сообщение об успехе («Оплата подтверждена + введите данные»),
  исключается из гашения (skip_message_ids) — не перезаписывается.
- Покрыты ВСЕ пути успеха: 4 кнопки «Проверить оплату» (TON/USDT/
  Tribute/Digiseller), Telegram Stars (successful_payment) и фоновые
  поллеры — гашение встроено в `_send_account_input_prompt` (main.py),
  через который проходят авто-подтверждения TON/USDT/Tribute/Digiseller,
  «воскрешённые» после таймаута заказы и recovery-таска.

#### 2. Дедуп кнопок меню — расширение `UserCommandDedupMiddleware`
- Повторное нажатие ТОЙ ЖЕ reply-кнопки (точный текст из MENU_BUTTONS:
  «Каталог», «Заказы», «Поддержка»…) стирает предыдущее нажатие.
  Каноничный пример владельца: столбик «Каталог» больше не растёт
  (сам экран каталога дедуплицировался ещё в v10).
- Ручной ввод «каталог» строчными / «зайди в каталог» — обычные
  сообщения, не стираются никогда. kind="m" не пересекается с командами.
- Админы и группы — как и раньше, не трогаются вовсе.

#### 3. Кулдаун «Проверить оплату» — 10 секунд
- Дорогая проверка (запрос к API) — не чаще раза в 10 с; при спаме юзер
  получает попап «⏳ Подождите N с…». Дешёвые попапы («Заказ не найден»,
  «Оплата уже подтверждена!») под кулдаун НЕ попадают — блокируется
  только реальный вызов API (note_check_press прямо перед verify).
- In-memory per-user реестр (кап 10000, FIFO).

#### 4. Устаревшие кнопки — `handlers/fallback_handlers.py` (НОВЫЙ)
- Catch-all callback-роутер, подключён ПОСЛЕДНИМ (после admin → support
  → user): сюда попадают ТОЛЬКО callback'и, не совпавшие ни с одним
  хендлером. Бот сразу отвечает попапом «Этот экран устарел — откройте
  меню заново» вместо молчаливых «часиков» на кнопке.
- Кнопки рабочих флоу (даже оплаченных/отменённых заказов) совпадают с
  настоящими хендлерами и получают осмысленные ответы — fallback их не
  перехватывает. Админские рабочие кнопки — тем более.

### Изменённые файлы
- `utils/payment_ux.py` — НОВЫЙ: реестр экранов, extinguish,
  extinguish_for_callback, кулдаун
- `handlers/fallback_handlers.py` — НОВЫЙ: catch-all для устаревших кнопок
- `handlers/user_handlers.py` — remember_screen ×7 (экраны+QR ton/usdt/
  digi/tribute), кулдаун ×4, extinguish ×5; без удалений
- `utils/chat_dedup.py` — дедуп нажатий кнопок меню (kind=m)
- `main.py` — `_extinguish_order_screens` в `_send_account_input_prompt`
  (3 точки), fallback_router подключён последним

### Тесты

гашение текст/фото/skip/без удалений, CallbackQuery-vs-Message ветки,

### UX №10 — Дедуп-реестр в SQLite (переживает рестарт)

- `utils/chat_dedup.py`: переход с monotonic на WALL-CLOCK (только
  wall-clock переживает сохранение в БД); write-behind — в памяти
  дельты `_dirty`/`_deleted`, фоновый `flusher_loop` сбрасывает их в
  SQLite раз в 30 с (пустая дельта = ноль запросов; сбой БД возвращает
  дельту в очередь); каждые ~10 минут чистятся просроченные строки.
- `load_registry` при старте (после db.init, только при включённом

## v15 (Task 35) — Ephemeral-растворение переходных сообщений + дедуп во всех чатах + Bot API 10.3

### Проблема
Владелец: «Почему сообщения не удаляются, ты же делал это? Даже дубли».
Диагностика нашла ДВЕ причины:

1. **Дедуп не действует в админских чатах.** По политике v10 (Task 25)
   «стираются только дубли» админ-чаты были полностью исключены — владелец
   тестирует на себе и видит ноль удалений.
2. **Каталог рандомизировал собственный текст при каждом открытии**:
   `get_social_proof_line()` вставлял `random.choice` из 3 шаблонов —
   сигнатуры каталога почти никогда не совпадали, дедуп каталога был
   фактически мёртв даже у обычных юзеров.

Плюс: автоудаление переходных сообщений (v4–v9) было снято в v10 —
подсказки/ошибки/команды оставались в чате навсегда.

### Решение (политика чата v15 — по группам, одобрено владельцем)

| Группа | Сообщения | Судьба |
|---|---|---|
| D — FSM-промпты | «Введите промокод», email, описание тикета | Пара «промпт + ввод» растворяется батчем после завершения ввода; без ответа — сами через 10 мин; неверный ввод + ошибка — через 15 с |
| E — ошибки | «Некорректный email», «Промокод недействителен», … | растворяются через 15 с (парами с вводом) |
| G — сообщения юзера | команды «/…» и нажатия кнопок меню | растворяются через ~5 с **во всех личных чатах, включая админские** |
| A/B/C/F/H — экраны, деньги, результаты, уведомления, админ-лог | каталог, оплаты, QR, карточки заказов, тикеты, рассылки | НЕ растворяются никогда |

### Что сделано
- **utils/ephemeral.py (новый движок)**: `schedule_erase` / `dissolve` /
  `dissolve_ids` (батч `deleteMessages` одним запросом, фолбэк по одному),
  `UserCommandCleanupMiddleware` (группа G), задержки v4–v9 наследованы
  (SUCCESS=5, INFO=6, ERROR=15, COMMAND=5, PAIR=2, PROMPT_TTL=600).
  Ошибки стирания всегда тихие — гигиена чата не может ничего сломать.
- **Нативные Ephemeral Messages (Bot API 10.3)**: `native_kwargs()`
  добавляет `ephemeral_message_parameters` (receiver_user_id /
  callback_query_id / replace_callback_query_message) к отправке промптов —
  жизнью сообщения управляет Telegram. Включается `.env →
  EPHEMERAL_NATIVE=true`; по умолчанию выключен (классика гарантирует
  доставку), при отказе API — тихий откат.
- **Дедуп починен**: каталог теперь рандомизирует шаблон соц-доказательства
  **1 раз в сутки** (`random.Random(ISO-дата)` — стабильно в течение дня и
  между рестартами, без состояния); счётчик покупок остаётся живым.
  Флаг `DEDUP_ADMINS=true` (по умолчанию) — дедуп работает и в админских
  чатах («во всех чатах»); false возвращает старое поведение.
- **Точки растворения**: промо (промпт/ошибка/ноль-цена/успех/отмена),
  email для чека (ввод растворяется — персональные данные), данные аккаунта
  (логины/пароли не висят в чате), поддержка (описание/уточнение — текст
  растворяется после сохранения в обращении, фото-скриншоты остаются),
  «Заказ не найден»-пары.
- **Пагинация на Bot API 10.3**: стрелки на границах и индикатор страницы —
  `disabled=DisabledButton()` (Telegram рисует их неактивными и не
  доставляет нажатия); callback «noop» сохранён для старых кэшированных
  клавиатур.
- Флаги в `.env.example`: `DEDUP_ADMINS`, `EPHEMERAL_ENABLED`,
  `EPHEMERAL_NATIVE`.

## v17 (Task 38) — полный аудит логики процессов: деньги, гонки, реклама

Комплексный аудит всего бота (три независимых обхода: админка, платёжный
контур, БД+поддержка+маркетинг) + исправления. Найдено 6 критичных и
~20 средних проблем; исправлены все критичные и ключевые средние.

### КРИТИЧНО: деньги и оплата

1. **Авто-отмена могла отменить ОПЛАЧЕННЫЙ заказ.** `cleanup_expired_orders`
   писал `cancelled` без CAS: poller подтверждал оплату между выборкой и
   апдейтом → оплаченный заказ «отменён», revive не срабатывал. Теперь
   строго `try_transition_order_status(pending_payment→cancelled)`.

2. **Фолбэк курсов возвращал 0.** Ключи `_rates_cache` существуют со
   стартовым значением 0 — дефолт `.get(key, 3.5)` был мёртвым кодом.
   При сбое CoinGecko+Toncenter: `usdt_to_rub()=0 ₽` → карточная ссылка
   Digiseller создавалась на МИНИМАЛЬНУЮ цену товара, а при
   `SKIP_AMOUNT_CHECK=true` (дефолт) такой платёж подтверждает заказ
   полностью — «выдача почти без оплаты». Теперь `or 3.5` / `or 90.0`.

3. **Реферальный бонус НЕ выплачивался ВООБЩЕ.** SQL в
   `_post_payment_actions` запрашивал несуществующую колонку
   `user_meta.referrer_id` (правильная — `referred_by`): исключение молча
   глоталось на КАЖДОЙ оплате. Обещание «бонус за друга» не работало ни
   разу. Колонка исправлена; бонус теперь платится ровно ОДИН раз
   (флаг `referral_bonus_paid`, миграция автоматическая) — раньше с
   еле-живым SQL параллельно существовала и проблема «бонус за каждую
   оплату» (фарм парами аккаунтов).

4. **Двойное подтверждение Digiseller по email.** Два pending-заказа с
   одним email (или общий/опечатанный email у двух юзеров): один платёж
   подтверждал ОБА заказа. Плюс инвойс мог «переиспользоваться» новым
   заказом. Теперь перед CAS проверяется, что инвойс не привязан к
   другому заказу (поллер и ручная проверка).

5. **Лимит промокода обходился авто-подтверждением.** Маркетинговые
   пост-экшены (лояльность, рефералка, списание used_count) вызывались
   ТОЛЬКО из ручных кнопок «Проверить оплату», а три фоновых поллера —
   ОСНОВНОЙ путь подтверждения — их не запускали: лимитированные
   промокоды оставались «неиспользованными». Пост-экшены теперь
   вызываются во всех точках подтверждения, включая revive; списание
   лимита атомарно (`UPDATE ... WHERE used_count < max_uses`).

6. **Двойная скидка за бонус друзей.** Каждый новый заказ резервировал
   ВЕСЬ бонусный баланс (списание при оплате): два заказа на один
   баланс → двойная скидка. Теперь учитывается резерв живых заказов

## v19 — конверсии из бота в Яндекс Директ (офлайн-конверсии Метрики)

Запрос владельца: «мне надо чтобы информация о конверсиях передавалась
в яндекс директ для настройки рекламных алгоритмов». Реализован
официальный канал: покупки бота выгружаются в Яндекс Метрику как
офлайн-конверсии (клэйм по yclid) → в Директе появляется цель с доходом →
автостратегии «Оплата за конверсии» optimizируют по реальным продажам.

### Как это работает (поток данных)

1. Объявление Директа ведёт на редирект бота:
   https://<адрес-бота>/r/?utm_source=yandex&utm_medium=cpc&utm_campaign=КАМПАНИЯ
   Директ сам добавляет yclid. Напрямую в Telegram его не донести
   (Telegram отдаёт боту только start-payload ≤ 64 символов) — поэтому
   новый хендлер /r/ (main.py, работает на health-сервере) сохраняет ВСЕ
   параметры клика в таблицу ad_clicks и отдаёт 302 на
   t.me/<bot>?start=c_<id> (короткий код).
2. /start c_<id>: бот разворачивает код из ad_clicks и сохраняет
   utm+yclid в utm_tracking (marketing.track_utm, новая колонка yclid).
3. Покупка (заказ → active): фоновый цикл services/metrica.py каждые
   METRICA_UPLOAD_INTERVAL сек (дефолт 900) собирает заказы с флагом 0,
   строит CSV (yclid,target,timestamp,price,currency) и POST-ит в
   https://api-metrica.yandex.net/management/v1/counter/{id}/offline_conversions/upload
   (Authorization: OAuth). Выгруженные → metrica_uploaded=1; заказы БЕЗ
   yclid (органика) → флаг 2, не пересканируются; при ошибке HTTP флаг
   НЕ ставится — выгрузка повторится на следующем цикле.
4. Метрика клэймит конверсию к визиту по yclid → в Директе появляется
   цель (имя = METRICA_TARGET_NAME, дефолт "purchase") с суммой.

### Что добавлено

- config.py: METRICA_COUNTER_ID, METRICA_OAUTH_TOKEN, METRICA_TARGET_NAME
  (purchase), METRICA_CURRENCY (USD), METRICA_UPLOAD_INTERVAL (900с),
  METRICA_ENABLED. Не заполнено → бот работает как раньше (no-op).
- services/metrica.py (новый): build_conversions_csv (чистая функция),
  upload_offline_conversions (403 → подсказка про токен, 400 → подсказка
  про «Загрузка данных»), upload_pending_conversions (идемпотентен),
  metrica_upload_loop (фоновый таск main.py).
- database.py: миграции utm_tracking.yclid, orders.metrica_uploaded;
  таблица ad_clicks; методы create_ad_click / get_ad_click /
  get_pending_metrica_conversions (JOIN utm_tracking, LIMIT 500) /
  mark_metrica_uploaded.
- main.py: маршрут GET /r → _ad_redirect (302, параметры → БД → короткий
  код); start_health_server(bot); таск metrica_upload.
- user_handlers.py: /start c_<id> → разворачивание параметров клика.
- marketing.py: track_utm хранит yclid (и строку с одним yclid без
  utm_source тоже).
- admin «Директ»: показывает статус выгрузки (счётчик/цель) либо
  подсказку настроить .env; рекомендованная рекламная ссылка через /r/.
- .env.example: блок METRICA_* с пошаговой настройкой.

### Что сделать владельцу (один раз, ~10 минут)

1. metrika.yandex.ru → создать счётчик (или взять существующий) →
   Настройка → «Загрузка данных» → включить «Офлайн-конверсии»
   (принять условия).
2. oauth.yandex.ru → приложение с доступом «Использование API
   Яндекс.Метрики» (metrica:write) → получить токен.
3. В .env: METRICA_COUNTER_ID, METRICA_OAUTH_TOKEN → рестарт бота.
4. В объявлениях Директа ставить ссылку
   https://<адрес-бота>/r/?utm_source=yandex&utm_medium=cpc&utm_campaign=ИМЯ
   (адрес бота = домен Render, если health-сервер запущен там).
5. Через несколько минут после первых продаж цель появится в Метрике;

## Автовосстановление: устаревшая сессия и «вечная загрузка» (v27.1)

Два реальных сценария с Render:

**1. «Сессия устарела» (чаще на компьютере).** Telegram подписывает
initData с auth_date, API принимает подпись не старше 60 минут
(защита от replay). Компьютер держит Mini App открытым часами —
после часа все запросы начинали получать 401, и юзеру приходилось
самому переоткрывать магазин.

Исправление:
- webapp_api.py: validate_init_data_ex() различает причины отказа —

  (битая подпись); _auth_err() добавляет в 401-ответ флаг

  initData). Защита от цикла перезагрузок — не чаще раза в 90 с;

## Сессионные токены: «сессия устарела» исчезает как класс (v27.3)

Жалоба: «выбираю тариф, жму оформить — всё равно сессия устарела».
Разбор показал три системных дефекта:

1. **Один текст на все отказы.** _auth_err() подписывала «Сессия
   устарела…» и при просрочке initData, и при БИТОЙ подписи (например
   неверный BOT_TOKEN на хостинге) — при диагностике это уводило не туда.
2. **Тишина в логах.** Валидация падала молча — в Render-логах не было
   ни строки, почему отказано. Теперь: bad signature (len, token_set)
   и expired (age, window) пишутся в лог с указанием причины.
3. **Перезагрузка не спасала.** handleSessionExpired() перезагружал
   страницу, но часть мобильных клиентов при reload подсовывает ТОТ ЖЕ
   старый initData — цикл с тостом «закройте магазин».

Решение (webapp_api.py):

- **make_session_token / verify_session_token** — подписанный токен
  `uid.exp.sig` (HMAC-SHA256 от секрета, выведенного из BOT_TOKEN,
  метка «WebAppSession»), TTL 7 дней (SESSION_TOKEN_TTL);
- **authenticate_user(body)** — единая авторизация для всех 5 мест:
  свежий initData → обычный путь; подпись валидна, но старше окна +
  совпадающий токен → пропуск (подпись Telegram уже проверена);
  initData бит/пуст + живой токен → пропуск; иначе отказ с причиной;
- **api_session выдаёт session_token** в ответе;
- **_auth_err**: expired → «Сессия устарела…» + expired:true (фронт
  молча перезагружается), invalid → «Не удалось подтвердить личность…».

Фронт (app.js): state.sessionToken хранится в localStorage
(tmaSessionToken), api() добавляет его во ВСЕ POST-запросы, ответ
/api/session обновляет токен (роллинг — сессия продлевается при
активности). handleSessionExpired остался как запас для токенов > 7 дней.

Безопасность: токен содержит только user_id и срок, выдаётся строго
после успешной проверки подписи initData, компрометация эквивалентна
компрометации initData и ограничена 7 днями; смена BOT_TOKEN инвалидирует
все сессии (секрет выводится из токена бота).

Проверено: scripts/test_session_tokens.py — 14 проверок (roundtrip,
подделка sig, подмена uid, просрочка, мусор, все ветки authenticate_user),
регрессия 27/27 PASS (тест токенов включён в общий прогон), py_compile,
node --check.
